# 里程碑 M1-13 docs-site 内容补充

## 1. 目标与范围

### 1.1 一句话

**把 M0 阶段只有 3 页骨架的 docs-site,补成 M1 GA 时面向最终用户的"完整用户文档"** — 涵盖安装 / 架构 / 模块 / API / 账号对接 / 二次开发 / 部署 / 计费说明 / FAQ / 更新日志共 9 大分组、约 30 个文档页。

### 1.2 与其他文档的关系

本 spec 与三类文档并存,**职责互不重叠**:

| 文档类型 | 受众 | 内容粒度 | 仓库位置 |
|---|---|---|---|
| **设计稿(本仓库 specs/)** | proapi 维护者 / 开发者 | 数据模型、接口契约、算法、实施步骤 | `docs/superpowers/specs/*.md` |
| **总体路线图** | 团队 / 投资人 | 阶段分期、关键决策 | `docs/superpowers/2026-05-21-proapi-总体路线图.md` |
| **用户文档站(本 spec 范围)** | proapi **终端用户**(部署者 / 二开者 / API 调用方) | 安装、配置、调用、故障排查 | `docs-site/zh/**`、`docs-site/en/**` |
| **CHANGELOG / CONTRIBUTING / SECURITY** | 协作者 | 仓库根目录 | 仓库根目录 |

**铁律**:
- `docs-site/` 不暴露 internal design 决策细节(如 "snowflake nodeID 分配")— 那些放 specs/
- `docs-site/` 不重复 README — README 只做 1 分钟 elevator pitch + 跳转到 docs-site
- specs/ 不写"如何运行 docker"— 那是 docs-site/zh/deployment/docker.md 的活

### 1.3 本 spec 的范围

属于本 spec 的(5 件事):

1. **定文档站信息架构**:9 大分组、30 个文档页的清单与路径

3. **定 sidebar 配置完整 TypeScript 代码**(可直接复制到 `.vitepress/config.ts`)
4. **定英文版策略**:M1 阶段英文目录与中文同构,正文留 placeholder + "Coming soon",M2 全量翻译
5. **定文档风格规范**:代码块语言、链接格式、截图占位、示例约定

不属于本 spec 的(明确边界):

- ❌ 不实际创建 `docs-site/zh/**` 任何 `.md` 文件 — 留给实施 plan 阶段照本 spec 大纲落地
- ❌ 不修改 `docs-site/zh/index.md` / `docs-site/zh/guide/introduction.md` / `docs-site/zh/guide/quickstart.md`(M0 已有,内容已可用)
- ❌ 不实现 Algolia DocSearch 接入(M2)
- ❌ 不实现版本切换器(M3,接 Mike 或同类工具)
- ❌ 不写 Playground / 在线试调(M2)
- ❌ 不做 PDF 导出(M3)

# 安装

> proapi 提供三种安装方式:Docker(推荐) / 预编译二进制 / 源码构建。本页介绍各自的步骤、适用场景与故障排查。

## 选哪种?

(1 段决策树:零运维选 Docker;轻量 VPS 不想装 Docker 选二进制;打算二开选源码。)

## 方式一:Docker 一键安装

### 拉取镜像
(`docker pull ghcr.io/proapi/proapi:latest` + 标签策略说明:latest / vX.Y.Z / vX.Y / vX)

### 准备配置文件
(`config.example.yaml` 下载链接,关键字段:database / redis / master_key)

### 启动
\`\`\`bash
docker run -d \
  --name proapi \
  -p 8080:8080 \
  -v $(pwd)/config.yaml:/app/config.yaml \
  -e PROAPI_MASTER_KEY=... \
  ghcr.io/proapi/proapi:latest
\`\`\`

### 验证
(`curl http://localhost:8080/healthz`)

## 方式二:预编译二进制

### 下载

(GitHub Release 链接占位 + 系统/架构对应表:linux-amd64 / linux-arm64 / darwin-amd64 / darwin-arm64 / windows-amd64)

\`\`\`bash
wget https://github.com/ijry/pro-api/releases/download/vX.Y.Z/proapi_linux_amd64.tar.gz
sha256sum -c proapi_linux_amd64.tar.gz.sha256
tar -xzf proapi_linux_amd64.tar.gz
chmod +x proapi
\`\`\`

### 准备依赖
(MySQL ≥ 8.0 或 PG ≥ 14 + Redis ≥ 6 + 一个空数据库)

### 配置
(同 Docker 的 `config.yaml`,放在 `./config.yaml` 或 `/etc/proapi/config.yaml`)

### 跑迁移
(`./proapi migrate up`)

### 启动
(`./proapi serve` 或注册为 systemd unit,提供 systemd unit 文件示例)

## 方式三:源码构建

### 环境要求
(Go 1.22+ / Node 20+ / pnpm 9 / make / git)

### 构建步骤
\`\`\`bash
git clone https://github.com/ijry/pro-api.git
cd proapi
make install-tools
make build           # 输出 ./bin/proapi
make web-build       # 构建 admin + user
\`\`\`

### 部署
(把 bin/proapi 与 web/admin/dist / web/user/dist 放服务器,同方式二启动)

## 验证安装

### `/healthz` 探活
(返回 JSON 含 status / version / build_time)

### `/metrics` Prometheus 端点
(默认开放,生产环境建议加 IP 限制 — 链 deployment/reverse-proxy)

### 后台首次登录
(`/admin` → 注册管理员账户)

## 常见故障

- "Error: PROAPI_MASTER_KEY required" → 见 configuration.md
- "Error: redis: dial tcp ...: connection refused" → Redis 未启动或 host/port 错
- "Error: failed to verify migration version" → 见 upgrade.md
- 镜像拉不下来 → 改用 dockerhub 镜像源或 GHCR 镜像加速
```

**关键要点 / 易忽略问题**

- Docker 镜像默认监听 8080,必须用 `-p` 暴露端口
- 二进制版需自备 MySQL/PG + Redis,proapi 不内嵌
- 源码构建需配置 `PROAPI_MASTER_KEY` 才能启动
- ARM Mac 必须用 `-platform linux/arm64` 拉镜像或自己编
- 任何方式都需要先跑 migration 再 serve;Docker 镜像入口已封装为 `migrate-then-serve`

# 配置

> proapi 的配置分两层:**启动配置**(yaml / env,只在启动时读) 与 **运行时配置**(`system_settings` 表,后台可改、热生效)。本页讲清两类配置的字段、默认值与使用场景。

## 配置加载优先级

(1 段:env > yaml > 默认值;读取顺序:`./config.yaml` → `/etc/proapi/config.yaml` → env 覆盖)

## 启动配置(config.yaml)

### node_id
(用途:Snowflake 节点号,集群必须每个实例不同;0-1023;单实例可不填,默认 0)

### master_key
(必填!base64 编码的 32 字节随机串,用于加密 channel credentials;
- 生成命令:`openssl rand -base64 32`
- 一旦确定不可换,换 key 后所有加密的 channel 凭证失效;
- env 名:`PROAPI_MASTER_KEY`,优先级高于 yaml)

### server
(addr / read_timeout / write_timeout / shutdown_timeout)

### log
(level / format=json|text / access_log_enabled)

### database
(driver=mysql|postgres / dsn / max_open / max_idle / max_lifetime / 完整 dsn 例)

### redis
(addr / db / password / pool_size / 完整 dsn 例)

### 完整 config.example.yaml
(贴一份带注释的范例)

## 运行时配置(system_settings 表)

> 这些 key 在数据库 `system_settings` 表里,后台 → 系统设置可改,改完所有节点 60 秒内生效。

(分组列出,每组一段引导 + 一张字段表 — 引用总纲 §7.2 但用 user-friendly 语言重写)

### auth.*
(allow_register / email_verification_required / github_oauth.* / password.*)

### session.*
(ttl_days / sliding)

### token.*
(default_rpm_limit / default_tpm_limit / prefix_show_len)

### pricing.*
(base_quota_per_dollar / exchange_rate_cny_per_usd)

### channel.*
(selector.mode / selector.max_retries / breaker.*)

### ratelimit.*
(user_default_* / ip_rpm / model_default_rpm / enabled)

### log.*
(retain_* / flush_*)

### notice.*
(show_max)

### billing.*
(reserve_ttl_seconds / reconcile_interval_seconds)

### manual_recharge.*
(enabled / exchange_rate / min/max_amount)

### redeem.*
(default_expires_days)

## 通过 API 改配置

(讲管理 API endpoint `PATCH /api/admin/settings/:key` 用法,链 api/admin-api)

## 环境变量速查表

| 用途 | env 名 | 等价 yaml |
|---|---|---|
| 加密 master key | `PROAPI_MASTER_KEY` | `master_key` |
| 节点号 | `PROAPI_NODE_ID` | `node_id` |
| DB DSN | `PROAPI_DATABASE_DSN` | `database.dsn` |
| Redis 地址 | `PROAPI_REDIS_ADDR` | `redis.addr` |
| 日志级别 | `PROAPI_LOG_LEVEL` | `log.level` |
```

**关键要点 / 易忽略问题**

- master_key 一旦丢失,channel credentials 全部解密失败,**必须备份**

```markdown
# 计费机制

> proapi 的计费基于 **预扣 + 提交**(Reserve + Commit)模式,所有变动通过 Redis Lua 脚本原子完成,辅以 DB 账本(ledger)做最终一致对账。

## 关键概念

(术语表:quota / ratio / wallet / reservation / ledger,引用总纲 §11)

## 计费单位

- **quota**:内部记账单位,整数,无小数
- **base_quota_per_dollar = 500000**:1 美元 = 500000 quota(可调,见 configuration)
- **ratio**:消费倍率,float,通常对应模型在上游的真实价

## 预扣 / 提交流程

```
[请求进入]
    │
    │  1. tokenize 入参 → input_tokens
    │  2. pricing.EstimateMax(model, in_tokens, max_out_tokens) → est_quota
    │
    ▼
[Reserve.lua]                     原子操作:wallet.balance -= est_quota,记 reservation
    │
    │   余额不足 → 返回 402
    │   余额够 → 继续
    │
    ▼
[选渠道 + 调上游]
    │
    │   失败 → Refund.lua(回滚预扣)→ 返回错误
    │   成功 → 拿到 usage
    │
    ▼
[Commit.lua]                      原子操作:wallet.consumed += actual,退还差额 = est - actual
    │
    ▼
[async ledger writer]             批量写 ledger_entries(append-only 账本)
[async log writer]                批量写 request_logs(含倍率快照)
```

## 倍率匹配顺序

(从最特定到最通用:group_model > model > group > global > catalog 默认)

## 流式响应如何计费

(简单讲流程:开始时按 max_out_tokens 预扣;读流时累计 out_tokens;流末 commit 实际值,自动退差额。)

## 退款规则

(三种情况:Refund.lua → 上游 5xx / 客户端断开 / 模型不存在)

## 对账与回收

(Reservation TTL 默认 10 分钟;reconcile job 每 30s 扫超时未 commit 的 reservation,自动 refund)

## 一致性保证

- Lua 原子 → 单 Redis 实例内一致
- DB ledger append-only → 可审计
- Wallet.balance 在 Redis 是热数据,DB 是 cold mirror,异步对账
- 极端故障(Redis 数据丢)的恢复方案:从 ledger 重放

## 多用户并发

(单 wallet 高并发用 Lua 序列化;不同 wallet 完全并行;Redis 单线程不构成瓶颈)
```

**关键要点 / 易忽略问题**

- "预扣"是为了避免长流式响应中余额耗尽却没法停止
- Lua 脚本必须幂等 — `commit.lua` 重复调用应该返回错误而不是再扣一次
- ledger 是 append-only,任何变动都新增一行,**禁止 UPDATE / DELETE**
- 跨实例时,Redis Cluster 模式下需要把 wallet key 与 reservation key 用 hashtag 绑到同一槽

# 限流策略

> proapi 用 Redis 滑动窗口算法实现 4 个维度的限流,所有维度并行检查,任一维度超限即拒绝。

## 4 个维度

| 维度 | key 命名 | 默认值 | 谁配 |
|---|---|---|---|
| user RPM | `ratelimit:user:{id}:rpm` | 60 | system_settings.ratelimit.user_default_rpm |
| user TPM | `ratelimit:user:{id}:tpm` | 100000 | system_settings.ratelimit.user_default_tpm |
| token RPM | `ratelimit:token:{id}:rpm` | 继承 user | api_tokens.rpm_limit |
| token TPM | `ratelimit:token:{id}:tpm` | 继承 user | api_tokens.tpm_limit |
| ip RPM | `ratelimit:ip:{ip24}:rpm` | 600 | system_settings.ratelimit.ip_rpm |
| model RPM | `ratelimit:model:{model}:rpm` | 0=不限 | system_settings.ratelimit.model_default_rpm |
| model TPM | `ratelimit:model:{model}:tpm` | 0=不限 | 同上 |

## 滑动窗口算法

(简介 ZSET 实现:每次请求加一条 (score=now_ms, member=now+rand);取 ZRANGEBYSCORE [now-window, now] 即当前窗口数;cost > 1 时多次 ZADD)

## RPM vs TPM

- **RPM**:每分钟请求数,cost=1
- **TPM**:每分钟 token 数,cost=tokens(在 chat 时 = input_tokens + max_out;在 commit 后修正)

## 优先级

(token-level 限制 > user-level;两者都生效时取更严的)

## 触发限流后

- HTTP 状态:429 Too Many Requests
- 响应 header:`X-RateLimit-Remaining`、`X-RateLimit-Reset`、`Retry-After`
- 错误 type:`rate_limit_exceeded`(OpenAI 兼容)

## 全局开关

`system_settings.ratelimit.enabled = false` 可关停所有限流(故障应急)。

## IP 维度的取值

- IPv4:取 /24 截断(减少误伤同公司用户)
- IPv6:取完整地址

## 关键运维

- Redis 故障 → 限流自动 fail-open(放行)
- 调高/低维度阈值不需要重启,setting 改完即生效
```

**关键要点 / 易忽略问题**

- IP /24 截断会让同一办公网的多用户共享配额,文档要说明
- TPM 用 input + max_out 预估,实际可能少消费 — 但限流是预扣,不会因为实际少而退回 token
- 单 Redis 实例瓶颈一般在 5w TPS+,M1 单点足够;M2 引入 Redis Cluster 或本地预扣 + 异步上报

# 渠道调度与熔断

> 当多家上游都能跑同一个模型时,proapi 用"优先级 + 加权随机"挑渠道,失败时自动重试别的渠道,连续失败会熔断让该渠道休息。

## 整体流程

(流程图:Select → Adapter.Chat → Success/Failure → Report → Breaker 状态更新)

## 选渠道算法

### 候选筛选

(条件:status=0 / 熔断 closed/half_open / 不在 excluded 列表 / tags 匹配)

### 优先级选择

(先取最高 priority 的所有渠道作为 pool)

### 加权随机

(在 pool 内按 weight 字段做加权随机抽样)

### 算法示例

```go
// 简化伪码
pool = highest_priority(active_channels)
total = sum(weights of pool)
r = rand(0, total)
for c in pool:
    if r < c.weight: return c
    r -= c.weight
```

## 故障转移

- M1 默认重试 3 次(`channel.selector.max_retries`)
- 失败渠道加入 excluded,**不会再选**
- 全部失败 → 返回上游错误码 + 提示用户

## 熔断器

### 状态机

(三态:CLOSED / OPEN / HALF_OPEN)

```
CLOSED  ──connection failures > threshold──▶ OPEN
OPEN    ──cool_down 到期──▶ HALF_OPEN
HALF_OPEN ──probe success──▶ CLOSED
HALF_OPEN ──probe failure──▶ OPEN
```

### 触发条件

- 计入失败:5xx / 网络错误 / 超时
- **不计**入失败:4xx 客户端错误(那是用户的锅,不是渠道的)

### 默认参数(可在 system_settings 改)

- `channel.breaker.window_seconds = 60`
- `channel.breaker.fail_threshold = 5`
- `channel.breaker.cool_down_seconds = 30`

### 半开探针

(HALF_OPEN 状态只放一个请求做探针,成功立即恢复,失败立即重新 OPEN)

## 集群广播

(状态变化时 PUBLISH proapi:channel:breaker {id, state};所有节点订阅刷新本地缓存,选渠道不再每次查 Redis)

## 后台运维

- 后台 → 渠道管理 → 看"熔断状态"列
- 可手动 "禁用 / 启用" 渠道(等价于强制 OPEN / CLOSED)
- 可重置熔断计数

## 监控指标

- `proapi_channel_select_total{provider, result=success|fail|breaker}`
- `proapi_channel_breaker_state{channel_id}` gauge(0=closed/1=open/2=half_open)
```

**关键要点 / 易忽略问题**

- 熔断会让那个渠道短时间内**完全不被选**,后台展示要醒目
- 半开期同时只放 1 个请求,所以恢复有滞后(< 1 秒级)
- 优先级和权重的语义易混淆:**priority 越大越优先**(不同优先级互不混选);**weight 在同一优先级内做加权随机**
- 重试导致用户实际等待变长 — 与超时配合调:总等待 ≤ user_timeout

# 定价与倍率

> proapi 通过 "tokens × ratio × group_ratio" 公式把上游 token 用量转换成内部 quota 消耗。本页讲清楚倍率是怎么算的、在哪改。

## 公式

```
quota = (input_tokens × input_ratio
       + output_tokens × output_ratio
       + cached_tokens × cached_ratio
       + reasoning_tokens × reasoning_ratio)
      × group_ratio
```

## 4 个 token 维度

| 维度 | 含义 | 何时有值 |
|---|---|---|
| input | 输入 tokens | 总有 |
| output | 输出 tokens | chat / completions 有,embeddings 没有 |
| cached | 命中缓存的 input | OpenAI prompt caching 命中时 |
| reasoning | 推理 tokens | o1/o3/deepseek-reasoner 等专用 |

## 倍率匹配的优先级

(从精确到通用,5 层匹配:)

1. **channel_model_mappings** 表的某行(input_ratio/output_ratio etc.)
2. **pricing_rules** scope='group_model'(用户分组 + 模型)
3. **pricing_rules** scope='model'(全局对该模型)
4. **pricing_rules** scope='group'(全局对该分组)
5. **pricing_rules** scope='global'(系统全局)
6. **model_catalogs.default_input_ratio**(模型字典默认值)
7. 1.0(兜底)

## 分组倍率 group_ratio

(独立一层,与 token 倍率相乘;用于"VIP 全场 8 折")

## 配倍率的方式

### 方式一:模型字典(全局默认)

(后台 → 模型字典 → 编辑某模型 → 改 default_input_ratio 等;影响全局)

### 方式二:pricing_rules

(后台 → 定价规则 → 新增,选 scope + 填倍率)

### 方式三:渠道级覆盖

(在某渠道的"模型映射"里改某模型的倍率;只影响走该渠道的请求)

### 方式四:分组倍率

(用户分组 → ratio 字段)

## 实例

(给 2 个例子:
1. 想给所有 gpt-4o 加 1.2 倍利润 → pricing_rules scope=model, model=gpt-4o, input_ratio=null, output_ratio=null, group_ratio = 1.2(用 group 表)
2. 想让 VIP 8 折 → user_groups vip 的 ratio 改 0.8)

## quota 与人民币 / 美元

(讲换算:base_quota_per_dollar = 500000(默认);1 quota = 0.002 美分)
```

**关键要点 / 易忽略问题**

- 4 个 token 维度的 ratio 都是 per-token 的乘数,不是百分比
- cached_ratio 默认 NULL,意味着"按 input 算",与 OpenAI 缓存定价(50% off)对齐:cached_ratio = 0.5 * input_ratio
- 渠道级倍率覆盖只对该渠道生效 — 一个用户调多个渠道时实际消费可能不同

# Docker Compose 部署

> 把 proapi + DB + Redis + Nginx 一把 compose 起,适合单机或小集群快速部署。

## 完整 compose 例

\`\`\`yaml
version: "3.9"

services:
  proapi:
    image: ghcr.io/proapi/proapi:vX.Y.Z
    container_name: proapi
    restart: unless-stopped
    depends_on:
      mysql:
        condition: service_healthy
      redis:
        condition: service_healthy
    environment:
      PROAPI_MASTER_KEY: ${PROAPI_MASTER_KEY}
      PROAPI_DATABASE_DSN: "user:pass@tcp(mysql:3306)/proapi?parseTime=true"
      PROAPI_REDIS_ADDR: "redis:6379"
    volumes:
      - ./config.yaml:/app/config.yaml:ro
    ports:
      - "8080:8080"

  mysql:
    image: mysql:8.0
    environment:
      MYSQL_ROOT_PASSWORD: rootpw
      MYSQL_DATABASE: proapi
      MYSQL_USER: proapi
      MYSQL_PASSWORD: pass
    volumes:
      - mysql-data:/var/lib/mysql
    healthcheck:
      test: ["CMD", "mysqladmin", "ping", "-h", "localhost"]
      interval: 5s
      timeout: 3s
      retries: 20

  redis:
    image: redis:7-alpine
    command: ["redis-server", "--maxmemory", "256mb", "--maxmemory-policy", "allkeys-lru"]
    volumes:
      - redis-data:/data
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 5s
      timeout: 3s
      retries: 20

  nginx:
    image: nginx:alpine
    depends_on:
      - proapi
    volumes:
      - ./nginx.conf:/etc/nginx/nginx.conf:ro
      - ./certs:/etc/nginx/certs:ro
    ports:
      - "80:80"
      - "443:443"

volumes:
  mysql-data:
  redis-data:
\`\`\`

## .env 文件

\`\`\`bash
PROAPI_MASTER_KEY=$(openssl rand -base64 32)
\`\`\`

## 启动

\`\`\`bash
docker compose up -d
docker compose logs -f proapi
\`\`\`

## 备份

\`\`\`bash
# DB
docker compose exec mysql mysqldump -uroot -prootpw proapi > backup-$(date +%F).sql

# Redis(可选,作为缓存可重建)
docker compose exec redis redis-cli --rdb /data/dump.rdb
\`\`\`

## 升级

(docker compose pull && docker compose up -d)

## 多节点扩展

(到 K8s / Nomad 时,把 proapi 横向扩展,DB / Redis 用托管;链 reverse-proxy)

## PG 版本 compose

(同上但 mysql 换成 postgres:14;DSN 用 `postgres://...`)
```

**关键要点 / 易忽略问题**

- depends_on + condition: service_healthy 确保 DB / Redis ready 才启动 proapi
- master_key 通过 .env 注入,不要直接写 compose
- redis 加 maxmemory + LRU 防止 OOM

```markdown
# 反向代理(Nginx / Caddy / Traefik)

> 生产环境一定要在 proapi 前面加反代,处理 TLS / gzip / 流式 buffering / 限流。本页给三种主流方案的完整示例。

## 为什么要反代

1. TLS 终止(proapi 默认 http)
2. 流式响应需要 **disable buffering**,否则用户感受不到流
3. 后台 UI / 用户 UI / API 不同路径分流
4. 加额外的 IP 限流 / WAF / CDN

## 关键配置点

- **SSE 流式**:必须关 buffering、调大 read/proxy_timeout
- **WebSocket**:M1 不用,M2 引入实时通知时加
- **Header 透传**:X-Forwarded-For / X-Real-IP / X-Request-ID
- **gzip**:对 JSON 响应开启,SSE 关闭

## Nginx 完整配置

\`\`\`nginx
upstream proapi {
    server 127.0.0.1:8080;
    keepalive 32;
}

server {
    listen 443 ssl http2;
    server_name api.example.com;
    ssl_certificate     /etc/nginx/certs/fullchain.pem;
    ssl_certificate_key /etc/nginx/certs/privkey.pem;

    # 流式响应必备
    proxy_buffering off;
    proxy_cache off;
    proxy_http_version 1.1;
    proxy_set_header Connection "";

    # 上行
    client_max_body_size 50m;     # vision 图片可能大
    proxy_read_timeout 600s;
    proxy_send_timeout 600s;

    # 透传
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;

    # API
    location /v1/ {
        proxy_pass http://proapi;
    }
    location /api/ {
        proxy_pass http://proapi;
    }
    location /healthz {
        proxy_pass http://proapi;
    }

    # /metrics 仅内网
    location /metrics {
        allow 10.0.0.0/8;
        deny all;
        proxy_pass http://proapi;
    }

    # 前端静态资源(假设 admin/user/docs 由 proapi 同实例服务)
    location / {
        proxy_pass http://proapi;
    }
}
\`\`\`

## Caddy 完整配置

\`\`\`caddyfile
api.example.com {
    encode gzip
    reverse_proxy 127.0.0.1:8080 {
        flush_interval -1   # 流式必备
        header_up X-Forwarded-For {http.request.remote.host}
        header_up X-Real-IP {http.request.remote.host}
    }
}
\`\`\`

## Traefik(Docker labels)

\`\`\`yaml
labels:
  - "traefik.enable=true"
  - "traefik.http.routers.proapi.rule=Host(\`api.example.com\`)"
  - "traefik.http.routers.proapi.entrypoints=websecure"
  - "traefik.http.routers.proapi.tls.certresolver=le"
  - "traefik.http.services.proapi.loadbalancer.server.port=8080"
  - "traefik.http.middlewares.proapi-stream.buffering.maxResponseBodyBytes=0"
  - "traefik.http.routers.proapi.middlewares=proapi-stream"
\`\`\`

## TLS 证书

- Let's Encrypt:certbot / Caddy 自动 / Traefik 自动
- 自签:见 deployment/docker-compose 的 certs 目录约定

## CDN

- 不建议把 /v1/ 走 CDN(SSE / 计费需要 origin 精确控制)
- 可以把 /admin /user 静态资源走 CDN

## 安全加固

- /metrics 只对监控网段开放
- 后台 /api/admin/* 加 IP 白名单 / VPN 限制
- 启用 fail2ban 防爆破 /api/auth/login
```

**关键要点 / 易忽略问题**

- SSE 反代最容易踩坑的是 buffering,必须显式关
- proxy_read_timeout 默认 60s,流式响应会被截断,要调到 600+ s
- X-Real-IP / X-Forwarded-For 必须透传,否则 proapi 的 IP 限流会全部限到反代 IP

**章节大纲**

```markdown
# 计费如何工作(用户视角)

> 这是给 proapi 终端用户(API 调用方)看的"我的钱怎么算"。

## 一次请求要花多少钱

公式:

```
钱 = (input tokens × input ratio
    + output tokens × output ratio
    + cached tokens × cached ratio
    + reasoning tokens × reasoning ratio)
   × 你的分组倍率
```

**简单理解**:你用了多少 token × 这个 token 类型的倍率 × 你的会员倍率。

## 举例

调一次 `gpt-4o`,输入 1000 token,输出 500 token,你是 `default` 分组(group_ratio = 1.0):

```
input  = 1000 × 1.0 = 1000
output = 500  × 3.0 = 1500
total  = 2500 quota = $0.005
```

(假定 gpt-4o input_ratio=1.0,output_ratio=3.0,均按 OpenAI 公开价倍数;实际以后台模型字典为准)

## quota 与人民币 / 美元

- 内部用 `quota` 整数记账,精度极高
- 默认换算:1 美元 = 500000 quota → 1 quota = 0.002 美分
- 部署方可能自定义,看后台"系统设置 → pricing"

## 看自己花了多少

- 用户前台 → 消费日志:每条请求的明细
- 用户前台 → 仪表盘:按天 / 按模型 / 按渠道聚合
- 公式倍率也在每条日志里"快照",可以追溯

## 余额不足怎么办

- HTTP 状态:402
- 错误:`insufficient_quota` / "余额不足,请充值"
- 充值方式见 [modules/payment](../modules/payment)

## 流式响应的特殊性

- 开始时按"最大可能消费"预扣
- 流结束按"实际消费"提交,自动退多扣的部分
- 中途断开:已发送的部分计费,未发送的退

## 缓存命中(prompt caching)

- OpenAI 的 prompt caching 命中时,cached tokens 用更低倍率(默认 input × 0.5)
- 节省的钱直接反映在你的账单上

## 推理 token(reasoning tokens)

- o1 / o3 / deepseek-reasoner 等会产生 reasoning_tokens
- 单独计费(通常等于或高于 output 倍率)

## 退款规则

- 上游 5xx / timeout / 网络错误 → proapi 不收钱,自动退还预扣
- 4xx 客户端错误(模型不存在、参数错)→ proapi 通常不收钱
- 成功调用 → 按实际消费收

## 我能控制什么

- 给令牌设额度上限(modules/token-system)
- 用便宜模型 / 用 cached prompts
- 给项目用不同令牌,方便分账

## 我看不到的

- proapi 部署方对你的定价规则(可能加价或打折,看后台 pricing_rules)
- 上游真实价格(对 proapi 部署方而言)— 你只看到你的最终价
```

**关键要点 / 易忽略问题**

- 用户最关心"贵不贵 / 钱花在哪"— 用具体例子带数字
- 强调"预扣 + 提交"避免误解长流式响应突然 402
- cached / reasoning token 比较新,要展开

```markdown
# 常见问题(FAQ)

## 1. proapi 与 one-api / new-api 有什么区别

(简短对比:proapi 强调三协议互转 / 企业级 SSO / 完整审计 / 现代技术栈;M2 后差距明显)

## 2. 是否支持 Anthropic / Gemini 入口

M1 仅 OpenAI 入口。Anthropic / Gemini 入口在 M2 加。出向(后端调用)9 家都支持。

## 3. 多个用户共享一个 GitHub 账号能行吗

不能。`oauth_bindings` 表 `UNIQUE (provider, provider_uid)`,一个 GitHub 账户对应一个 proapi 账户。

## 4. 调用突然 402 Insufficient Quota

- 检查钱包余额(用户前台 → 仪表盘)
- 检查令牌额度上限(单令牌可能设了 quota_limit)
- 流式请求会预扣 max_tokens 估算量,长流式可能比想象多

## 5. 如何提高单令牌的 RPM / TPM

- 用户前台 → 令牌 → 编辑 → 设 rpm_limit / tpm_limit;0 = 用 user 默认
- 系统级默认在 `system_settings.ratelimit.*`

## 6. 渠道熔断后多久会自动恢复

默认 `cool_down_seconds = 30` 秒。也可以后台手动重置熔断。

## 7. master_key 丢了怎么办

灾难场景。所有渠道凭证(credentials)无法解密,等于全部要重填。建议**永远备份 master_key 到密码管理器**。

## 8. 支持多实例集群部署吗

支持。前提:
- 同一份 `master_key`
- 同一个 DB / Redis
- 每个实例 `node_id` 唯一(否则 Snowflake ID 冲突)

## 9. 默认有哪些用户分组

`default`(ratio=1.0) / `vip`(ratio=0.8) / `svip`(ratio=0.6),seed 阶段写入,可改可删可加。

## 10. 文档站可以离线部署吗

可以。`pnpm --filter docs-site build` 后,`docs-site/.vitepress/dist/` 静态文件丢任意 web server。
```

**关键要点 / 易忽略问题**

- 10 个问题覆盖最高频的运维 / 用户 / 部署疑问
- 每个问题答案 1-3 段,避免冗长

## 7. 风格规范

### 7.1 markdown 写作

- **每页 H1 与 frontmatter title 一致**,VitePress 会自动隐藏 H1 重复
- **`outline: deep`** 用于长页(installation / configuration / openai-compat / channel-management 等),其他页面默认即可
- **段落 ≤ 4 行**;长段落拆 subsection
- **强调用粗体**,术语第一次出现用 `code`
- **避免"我们 / 你"混用**:用"你"称用户,主语用"proapi"指本系统

### 7.2 代码块

- **必须标语言**:` ```bash / ```go / ```yaml / ```sql / ```ts / ```javascript / ```python / ```json / ```nginx / ```lua / ```caddyfile`
- 不标 → CI lint 失败(M2 加 markdownlint 强制)
- 行长 ≤ 100 字符,过长用 `\` 换行
- 命令行块以 `$` 开头时,**用户可复制部分不带 `$`**

### 7.3 链接

- 站内同语言:相对路径,如 `[安装](./installation)`(VitePress cleanUrls)
- 站内跨分组:绝对路径,如 `[渠道管理](/zh/modules/channel-management)`
- 跨语言:绝对路径,如 `[English](/en/guide/installation)`
- 外站:完整 URL + 在新 tab 打开(VitePress 默认行为)
- 链到仓库根:`https://github.com/ijry/pro-api/blob/main/CHANGELOG.md`

### 7.4 截图

- M1 阶段允许 **占位符**:用 markdown `> (截图占位:xxx)` 或 `![screenshot](.... TBD)`
- M2 阶段在 `docs-site/public/screenshots/` 放真实截图,统一 1280×800 / @2x
- 截图必须脱敏(无真实 token / 邮箱 / IP)

### 7.5 表格

- 列对齐:`|---|---|---|`
- 长表格(> 10 行)前后留空行
- 数据来源在表后用 `> Source: ...` 注明

### 7.6 callout 块

VitePress 自带 `:::tip` / `:::warning` / `:::danger` / `:::info` / `:::details`,本 spec 推荐:

```markdown
:::warning 数据丢失风险
master_key 一旦丢失,所有渠道凭证不可解密。请在密码管理器或 HSM 中备份。
:::
```

约定:
- **danger**:数据丢失 / 安全风险
- **warning**:不可逆操作 / 重要前提
- **tip**:小技巧
- **info**:补充背景
- **details**:可折叠的长内容(如完整配置文件)

### 7.7 示例约定

- 占位 token 统一 `pa-xxx`(不暴露真 token 格式长度)
- 占位 host 统一 `api.example.com` / `proapi.example.com`(避免 IP)
- 示例邮箱 `user@example.com`
- 示例金额用 100 / 1000 / 10000 这样的整数,易读

### 7.8 文件命名

- 全小写,kebab-case
- 与 sidebar text 不必完全一致,但语义清楚:`channel-scheduling.md` 对应"渠道调度与熔断"
- 复数 / 单数:统一用单数(`installation.md` 而非 `installations.md`),除非概念本身就是复数(`integration/oauth-github.md`)

### 7.9 metadata 区分

- spec 文件 frontmatter 字段:`name / description / created_at / status / 依赖 / 被依赖`
- docs-site 页面 frontmatter 字段:`title / outline`(可加 `description` 给 SEO)
- 不要把 spec 元数据写到 docs-site,反之亦然

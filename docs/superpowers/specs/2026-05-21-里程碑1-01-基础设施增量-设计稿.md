# 里程碑 M1-01 基础设施增量

## 1. 目标与范围

### 1.1 一句话

**M1 启动前的"地基"** — 把 M0 已有的零散组件粘成一个可注入的 application context,加上 M1 所有业务模块共享的基础能力。

### 1.2 范围

属于本 spec 的(8 件事):

1. **DI 装配**:`internal/app/application.go` — application 容器、初始化顺序、优雅关停
2. **Lua 脚本加载器**:`internal/cache/lua.go` — Lua 脚本注册 / EVALSHA / 重连后自动回填
3. **setting 框架**:`internal/setting/` — 三层缓存(本地 → Redis → DB)+ Pub/Sub 失效
4. **错误响应中间件**:`internal/server/middleware/error.go` — `*apierr.Error` → JSON,代理 API 走 OpenAI 协议错误格式,管理 API 走 `{code, message}` 格式
5. **错误码扩展**:`pkg/apierr/codes.go` 新增 8 个 M1 必备错误码 + i18n 消息
6. **clock 抽象**:`internal/util/clock/` — 可注入时钟,便于测试
7. **tokenizer 抽象**:`internal/util/tokenize/` — 接口 + tiktoken 实现 + 字符级 fallback
8. **种子数据 SQL**:`migrations/{mysql,postgres}/000022_seed_initial.{up,down}.sql` — 默认分组/系统设置默认值

不属于本 spec 的(明确边界):

- ❌ `system_settings / audit_logs` 表 DDL(放本 spec 但仅 schema;业务使用在各自模块 spec)
- ❌ asynq 任务系统(M2 才用)
- ❌ Otel(M3)
- ❌ admin / user 后台 handler(各自模块 spec)
- ❌ middleware 链中的 TokenAuth / SessionAuth / RateLimit / RoleGate(在 M1-02/03/07 spec)

## 3. 接口契约

### 3.1 cache.LuaScripts

```go
// internal/cache/lua.go
package cache

import (
    "context"
    "fmt"

    "github.com/redis/go-redis/v9"
)

// LuaScript 是一个已加载到 Redis 的脚本。
type LuaScript struct {
    name string         // 用于日志
    src  string
    sha  string         // 首次 Load 后填
    rdb  *redis.Client
}

// LoadScript 加载并 SCRIPT LOAD 一段脚本,失败返回 error。
// 同一脚本多次 LoadScript 是幂等的(SHA 相同)。
func LoadScript(ctx context.Context, rdb *redis.Client, name, src string) (*LuaScript, error)

// Run 执行脚本,优先 EVALSHA,NOSCRIPT 时自动 fallback 到 EVAL 并刷新 SHA。
func (l *LuaScript) Run(ctx context.Context, keys []string, args ...any) (any, error)

// RunInts 是 Run 的便利包装,要求脚本返回 []int64。
func (l *LuaScript) RunInts(ctx context.Context, keys []string, args ...any) ([]int64, error)
```

实现要点:
- 失败重试:`NOSCRIPT` 错误时,重新 EVAL(自带 LOAD)
- 并发安全:`LuaScript` 内部不可变(`sha` 在加载时一次性设)
- 日志:LOAD 时打印 `lua script loaded` + name + sha 前 8 位

//
// 顺序:
//   1. crypto from master_key
//   2. idgen from node_id
//   3. orm.Open

func SetupBasic(ctx context.Context, cfg *config.Config, log *zap.Logger) (*Application, error) {
    app := &Application{Config: cfg, Log: log}
    
    crypto, err := crypto.NewAESGCM(decodeKey(cfg.MasterKey))
    if err != nil { return nil, fmt.Errorf("crypto: %w", err) }
    app.Crypto = crypto

## 4. 关键算法

### 4.1 Setting 三层缓存

```
读路径(Get):
  本地一级缓存(sync.Map + TTL 60s) → 命中返回
  ↓ miss
  Redis GET setting:{key}            → 命中,回填本地,返回
  ↓ miss
  DB SELECT                          → 命中,回填 Redis(TTL 10min)+ 本地,返回
  ↓ miss
  返回 ErrNotFound

写路径(Put):
  DB UPSERT
  ↓ success
  Redis DEL setting:{key}            (失效远端缓存)
  Redis PUBLISH proapi:setting:invalidate "{key}"
  ↓ Pub/Sub 订阅者(包括自己)收到
  本地 sync.Map Delete "{key}"
```

并发场景考虑:
- **读写并发**:写完 DB 后才 DEL Redis + PUBLISH,中间窗口可能有读到旧值。可接受(setting 改动不频繁,最终一致 < 60s 即可)
- **多实例并发写**:DB 唯一 PK(key)+ UPSERT,顺序由 DB 决定。Pub/Sub 多次 PUBLISH 等价于一次 — 都失效缓存
- **Pub/Sub 丢消息**:Redis Pub/Sub 是 best-effort,本地缓存有 60s TTL 兜底

### 4.2 本地缓存数据结构

```go
type cachedValue struct {
    raw json.RawMessage
    ts  time.Time  // 写入时间;TTL 检查用 clock.Now() - ts
}
```

`sync.Map.Load` 后判断 `clock.Now().Sub(v.ts) > ttl` 则视为 miss,继续走 Redis。

### 4.3 LuaScript 自动重连

`go-redis` 在 Redis 重启后会重新连接,但 Redis 端 SCRIPT FLUSH 后所有 SHA 都失效。`LuaScript.Run` 检测 `redis.Nil` + `NOSCRIPT` → fallback 到 EVAL:

```go
func (l *LuaScript) Run(ctx context.Context, keys []string, args ...any) (any, error) {
    r, err := l.rdb.EvalSha(ctx, l.sha, keys, args...).Result()
    if err == nil { return r, nil }
    if !isNoScript(err) { return nil, err }
    // NOSCRIPT — 重新 EVAL(自带 LOAD)
    r, err = l.rdb.Eval(ctx, l.src, keys, args...).Result()
    if err != nil { return nil, err }
    return r, nil
}

func isNoScript(err error) bool {
    return err != nil && strings.HasPrefix(err.Error(), "NOSCRIPT")
}
```

### 4.4 错误响应中间件

`ErrorResponse` 中间件统一吸收 handler 返回的 `*apierr.Error`。Gin 不支持 handler 直接返回 error,所以约定:**handler 把 error 写到 `c.Set("err", e)` 然后 `return`**,中间件后置处理。

```go
// internal/server/middleware/error.go
package middleware

import (
    "net/http"

    "github.com/gin-gonic/gin"
    "github.com/ijry/pro-api/pkg/apierr"
)

const errCtxKey = "proapi:err"

// SetErr 由 handler 调用,在 ctx 标记错误。
func SetErr(c *gin.Context, e *apierr.Error) {
    c.Set(errCtxKey, e)
    c.Abort()
}

// ErrorResponse 是 trailing 中间件,在 handler return 后渲染错误响应。
//   format = "openai"  → 代理 API 风格
//   format = "json"    → 管理 API 风格 {code,message,details}
func ErrorResponse(format string) gin.HandlerFunc {
    return func(c *gin.Context) {
        c.Next()
        v, ok := c.Get(errCtxKey)
        if !ok { return }
        e, ok := v.(*apierr.Error)
        if !ok { return }
        switch format {
        case "openai":
            c.JSON(e.HTTPStatus, openAIErrorBody(e))
        default:
            c.JSON(e.HTTPStatus, gin.H{
                "code":    int(e.Code),
                "message": e.Message,
                "details": e.Details,
            })
        }
    }
}

func openAIErrorBody(e *apierr.Error) gin.H {
    return gin.H{
        "error": gin.H{
            "message": e.Message,
            "type":    openAIErrorType(e.Code),
            "code":    openAIErrorCode(e.Code),
        },
    }
}
```

### 4.6 PG/MySQL JSON 类型适配

GORM 默认 `type:json`,在 MySQL 是 `JSON` 列,在 PG 是 `TEXT`(不优)。我们重写 PG dialector 让 `type:json` → `JSONB`:

```go
// internal/orm/dialect.go
package orm

import (
    "gorm.io/gorm/schema"
)

// PGNamingStrategy 没有 column 重写需要,直接用默认 NamingStrategy。
// 关键:在 GORM dialector 注册时,Postgres dialector 把 column 的 "type:json" 替换为 "jsonb"。

// 实际方案:使用 gorm.io/datatypes 的 datatypes.JSON 类型在 model 字段(MySQL/PG 通吃)。
```

**决策**:用 `json.RawMessage` + GORM tag `type:json`,在 GORM hook 里:

```go
// Open() 内增加:
db.Callback().Create().Before("gorm:create").Register("proapi:json_to_jsonb", jsonToJSONBPG)
db.Callback().Update().Before("gorm:update").Register("proapi:json_to_jsonb_u", jsonToJSONBPG)
```

实现略复杂。**简化方案**:每个表的 PG migration 显式写 `JSONB`(像 §2.1 那样),GORM 端字段类型 `json.RawMessage` 对两个驱动都能正确读写。Tag 留空或写 `gorm:"type:json"` MySQL 用,PG 由 schema 决定 — schema 已经是 JSONB,GORM 无需自动建表。

**采纳**:migrations 写死 `JSON / JSONB`,GORM disable AutoMigrate(M1 不开 AutoMigrate),完全靠 SQL 文件维护 schema。
